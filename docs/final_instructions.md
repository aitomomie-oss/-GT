# Codex開発指示書｜MY AI ASSET（確定版）

作成日：2026年10月19日  
対象：個人利用／Windows PC／ローカルWebアプリ

## 0. Codexへの最重要指示

あなたは金融データ管理、Python、Streamlit、データ品質管理、セキュリティに精通したシニアエンジニアです。以下の仕様に従い、**設計案だけで終えず、起動・操作・テストできる実物**を実装してください。

- 不明な証券会社のCSV列仕様やAPI仕様を推測して「対応済み」としない。まずサンプル・実ファイルのヘッダーを確認し、列マッピングを構成可能にする。未対応形式は安全に停止し、手入力画面を提供する。
- 外部サービスの認証情報、証券会社のログインID・パスワード・ワンタイムコードを要求・保存しない。スクレイピングや非公式な自動ログイン、売買注文を実装しない。
- 外部有料APIなしでローカル完結するMVPを優先する。生成AI API連携および自動発注はMVPの対象外。
- 計算根拠、データ取得日時、欠損データを常に可視化し、「不明」を適切に表示する。利益保証、的中率・上昇確率の捏造をしない。
- 開発中の実データはGitにコミットしない。架空データのみリポジトリに含める。
- 一度に作れない場合はMVPを優先し、実装済み・未実装・テスト済みを明確に区別する。

## 1. 利用者・目的・スコープ

- 証券会社：SBI証券／PayPay証券。**NISA口座はSBI証券**。PayPay証券の保有口座は課税口座として初期設定し、口座種別は修正可能にする。
- 保有資産：投資信託、個別株（日本株／米国株）。ETFにも拡張可能な設計とする。
- 積立予算：月額5,000～10,000円を標準レンジとし、月ごとに変更可能。初期値7,500円。これは投資目標ではなく支出上限。
- 方針：長期分散積立を中核とし、個別株は既存保有管理と任意の追加購入検討にとどめる。
- 目的：2社の資産一元管理、投資元本・評価損益・入出金の区別、積立進捗、資産配分と重複の可視化、分散・費用リスクのチェック、将来のシナリオ比較。
- 初期版（MVP）：単一ユーザー、PC上の localhost で起動。インターネットに公開しない。
- 対象外：証券会社との自動売買、口座の認証連携、リアルタイム全銘柄データ、未検証のAIによる買い推奨、税務申告・正式な税額計算、FXや仮想通貨への投資実行。

## 3. UI設計（6画面）

全画面は日本語。PC画面幅を活かした見やすいカード式UI、上部ナビ、表の検索・絞り込み・ソート、エラー時の日本語メッセージ、更新日時の明示。最低限キーボード操作にも対応。画面幅が狭い場合にも表・文字が重ならないこと。

### 3.1 ホーム
- 総資産評価額、投資元本（区分を明示）、含み損益（額／率）、現金残高、当月積立予算・実績・残額。
- 証券会社別、資産分類別（投信／日本株／米国株／現金）、口座種別別の内訳。
- 評価額と累積外部拠出額の推移。履歴不足時はグラフを捏造せず「取得できる時点から表示」とする。
- 最終更新日時、価格未更新／円換算に必要な為替情報欠落時の警告。

### 3.2 保有資産
- 銘柄・投資信託名、コード、証券会社、NISA／特定／一般、通貨、数量、平均取得単価、現在単価、時価評価額、含み損益、評価日を表示。
- 明細の手入力・編集・削除、評価額スナップショットの入力、売買履歴の参照。
- 数量と基準価額単位の差異を明示。投資信託の基準価額が1万口当たりなら `数量÷10,000×基準価額` で評価する。
- 米国株はUSD時価と日本円評価額の両方を表示し、使用したUSD/JPYと日付を必ず表示。

### 3.3 積立プラン
- 月別予算を標準5,000〜10,000円の範囲で設定、必要に応じ任意金額へ変更可能。
- 商品別の予定積立額、買付先、予定日、進捗、月内残予算、未実施分を表示。
- 初期提案は「SBI証券NISAの長期積立を優先」。個別株枠を強制しない。80/20等の固定配分を押し付けず、利用者が調整可能。
- 買付予定と実際の約定を分ける。予算超過警告とNISA口座区分の不整合警告を実装。

### 3.4 AI分析
- **MVPは説明可能なルールベース分析**を採用。判定種別は「確認推奨／注意／情報不足／問題なし」。投資助言のような確定的な「買え／売れ」は表示しない。
- 評価条件：①月予算超過 ②銘柄・地域への集中 ③投信と個別株の実質的な重複の可能性 ④運用コストの入力有無と比較 ⑤リスク許容度との乖離 ⑥価格・為替データの古さ ⑦積立予定の実行状況。
- 単一銘柄が保有資産の30%を超える場合などは「初期警告の例」として設定可能なしきい値で扱う。投資信託の構成銘柄の重なりは構成データがない限り断定しない。
- 各判定は入力値・計算式・適用基準・利用日時・制約を説明。データ不足時は判定不可とする。
- 生成AI連携は将来のオプション。MVPでは外部への個人金融情報送信なし。

### 3.5 資産シミュレーション
- 現在の評価額、月額積立5,000／7,500／10,000円等、年率シナリオ -3%、0%、3%、5%を切替可能にする。
- 5年／10年／20年を比較し、将来評価額・拠出元本・損益差分をグラフ化。
- 年率は予想値ではなく仮定値と明記。月率 `(1 + 年率)^(1/12) - 1` で換算する。毎月末に積み立てる計算を初期条件とし、前提条件を画面に記載。
- 税金、為替変動、手数料、インフレの扱いを明示し、未考慮項目は注記する。

### 3.6 データ管理
- 口座登録、ファイルアップロード、列マッピングプレビュー、取り込み確認、エラーログ、取り込み履歴・取り消し、バックアップ・復元。
- SBI証券：公式にダウンロードした取引CSVを入力対象とする。株式約定履歴と投資信託履歴等は様式が異なるため個別アダプター化。対応列が確定していないものは汎用CSVマッピング画面で取り込む。
- PayPay証券：公式の電子交付書面（取引報告書、取引残高報告書）に基づく手入力・テキストPDFの解析補助を実装。アプリとミニアプリの書面の差異に注意。PDF自動解析が信頼できない場合は検証画面で確定させる。
- 一度取り込んだ明細を再取り込みしても重複計上しない。同一ファイル／同一取引の可能性を表示。削除ではなく取り込み単位で安全に取り消せる。
- データは手入力だけでも全画面を利用可能にする。

## 4. DB設計とデータ整合性

最低限以下のテーブルを設計し、適切なユニーク制約、外部キー、インデックスを設ける。

- `accounts`：ID、証券会社、口座種別、NISA枠種別、通貨、ステータス。
- `instruments`：ID、銘柄コード／ISIN（任意）、名称、商品種別、通貨、価格単位、分類、信託報酬（不明許容）。
- `transactions`：口座、商品、約定日時、取引種別（買付・売却・分配金・配当・手数料等）、数量、単価、税額、費用、約定金額、通貨、取り込み元・外部識別子。
- `cashflows`：口座の外部入金・外部出金・口座間振替（相手口座IDを任意で保持）。運用損益と区別。
- `positions`：口座・商品・評価日ごとの現在残高／数量・参考取得原価・由来（取引から計算／残高直接入力）。
- `quotes`：銘柄別・日時別の価格、通貨、価格単位、情報源、更新日。
- `fx_rates`：通貨ペア、適用日時、レート、情報源。
- `budgets`：対象年月、予算額、通貨。
- `savings_plans`：商品、口座、予定日、予定額、ステータス。
- `import_batches` / `import_rows`：ファイルハッシュ、取引識別、マッピング設定、成功件数・失敗件数、取消ステータス。
- `analysis_results`：評価日、ルールID、判定、根拠、参照データ更新日。

**二重計上防止規則：** 取引明細から算出した保有残高と、残高報告書から入力した時点残高は加算しない。後者は残高照合・初期残高設定に利用する。「取得原価不明」の残高から根拠のない損益を逆算しない。証券会社が算出した税務上の損益とアプリの参考損益を区別する。

**計算規則：**
- 株式評価額＝数量×1株価格。投信評価額＝保有口数÷表示口数単位×基準価額。
- 外貨建評価額の円換算＝外貨建評価額×評価日に対応する為替レート。為替未取得なら円評価額は「計算不可」。
- 含み損益＝時価評価額−参考取得原価。取得原価が不明なら「計算不可」。
- 拠出元本＝外部からの入金−外部への出金（口座間振替は除外）。単純な「購入額合計」を拠出元本と呼ばない。
- 累積運用損益の把握には現金、資産、外部資金移動、配当・分配金、売却等を整合させる。データ不足時は「参考値」と表示。
- 売却損益計算は移動平均による参考値を初期実装とし、税務上の公式損益と混同しない。株式分割・併合、再投資分配金、手数料などを扱う拡張ポイントを設ける。
- 異常データ（負の数量、日付不正、通貨不一致、同一キー重複）を検出し、勝手に補完しない。

## 5. データ取得と法令・利用条件

- 公式画面から**利用者が取得した**CSV／PDFを原則とする。公式APIがない証券口座について、非公開API解析やブラウザ自動ログインは行わない。
- 市場価格更新は「手入力」「CSV取込」をMVPの確実な経路とする。将来J-Quants API V2等をアダプター追加できるよう抽象化する。Freeプランは12週間遅延があるため最新株価として扱わない。
- 日本のNISA制度について、NISA口座は利用者ごとに原則1口座で、対象金融機関はSBI証券として設定。税制・限度額の詳細は設定値として持ち、制度改正に対応できるようハードコードしない。NISA残り枠は取引履歴が不完全なら推計値と表示する。
- 外部APIの利用条件、商用／個人利用条件、表示再配布制限を守る。

## 6. セキュリティ・個人情報

- Streamlitを `127.0.0.1` バインドで動作させる。クラウド公開しない。
- `local_data/`、アップロードファイル、DB、バックアップ、`.env`、秘密情報を`.gitignore`に登録。ログに取引明細全文・個人名・口座番号を出さない。
- インポートファイルをパス指定で外部任意ファイルにアクセスさせない。拡張子・サイズ・列・データ形式を検査する。
- 元ファイルを残すか自動削除するかを設定可能にし、初期値は取り込み後の一時ファイル削除。バックアップ・復元時は確認画面を出す。
- 証券会社のログイン情報・二段階認証情報は入力・保存・取得しない。送信先不明の外部AI APIを使わない。

## 7. 実装順序

1. **Phase 1｜動くMVP**：フォルダ、環境設定、DB、サンプルデータ、6画面の枠、手入力、残高・損益表示、予算管理。
2. **Phase 2｜取り込みと整合性**：汎用CSVマッパー、SBIの確認済みフォーマット、PayPay書面の入力補助、重複検出、残高照合、取り消し。
3. **Phase 3｜AI分析・シミュレーション**：説明可能な分析ルール、条件設定、複数シナリオ、グラフ、PDF等へのエクスポートは任意。
4. **Phase 4｜品質向上**：データ検証、UI改善、エラーハンドリング、バックアップ復元、README整備、Windows起動テスト。
5. **Phase 5｜後日拡張**：公式市場データの任意連携、個別株研究、通知、機械学習を段階的に追加。MVP完成条件には含めない。

## 8. テストと合格基準

最低限pytestで以下を自動テストし、画面での手動検証も行う。

1. 2つの口座に同じ銘柄を持つ場合、口座別に表示され合計は正しい。
2. NISA口座がSBI証券に設定され、PayPay証券の積立に誤ってNISA枠を使わない。
3. 5000、7500、10000円の予算で、積立予定額・実績・残額が一致。月額予算変更が過去月を改変しない。
4. 同じ取引CSVを2度取り込んでも残高が増えない。取り込みエラー後に半端なレコードが残らない。
5. 投資信託の1万口基準価額、個別株の株数、米国株のUSD/JPY換算が期待値に一致。
6. データ不足・古い株価・不明な取得原価・為替欠落では、適切に「未取得／計算不可」と表示する。
7. 売買・入出金・口座間振替・配当を二重計上しない。損益と現金移動を分ける。
8. 年率マイナスを含むシミュレーションで、初期値・積立総額・最終額・グラフが整合する。
9. DBバックアップと復元後の主要件数・合計が一致する。
10. 起動後、6画面にアクセスでき、コンソールに未処理例外が出ない。

**完成条件：** `pip install -r requirements.txt` で導入し、`streamlit run app.py --server.address 127.0.0.1` でWindows上に起動できる。サンプルデータは画面上で「架空」と明示。`pytest` 実行結果、未実装機能、残課題をREADMEに記録する。テスト未実施なら完了と報告しない。
