# 安全な開発計画

## 0. 実装開始前に完了させる条件

1. ユーザー申告のWindowsフォルダーを、稼働プロセスのPythonと既存の安全な設定診断に照合する。
2. クラウドの基準コミットとWindows側のコードを比較する。フォルダーの日付やダウンロードしたZIPの名前だけで版を決めない。
3. 起動バッチが作業フォルダーとDB変数をどう扱うかを確認する。別PowerShellの環境変数だけで稼働アプリの参照先を断定しない。
4. 実際に使用しているDBを一つに特定する。候補が複数ある、または保存先不明なら、そのまま止めて調べる。DBを新規作成して穴埋めしない。
5. 対象アプリを停止し、コード・使用中DB・設定のバックアップを作成して検証する。旧DBやsecretsをクラウドへアップロードさせない。
6. 今回の調査結果を報告する。この段階ではNEXTの機能実装を始めない。

**今回の到達点**：指定Windowsフォルダー、4ファイルのハッシュ、この起動.batで選ばれるDB、プロジェクトキーの読取条件を確認し、コード・DB・設定のバックアップと別パスへのDB復元検証の成功結果を受領しました。今回の調査・保全・設計の結果として報告します。

**実装開始前に残る確認**：Windows全ソースとクラウド版との差分、コピーDBの実スキーマ、評価履歴機能の有無。過去の8501番の接続元とAPI認証は未確認です。既存Windows版をクラウド最新版と同一だと仮定して移行しません。本番への変更やNEXTの機能実装は今回の対象に含めず、報告後の次の依頼で範囲を定めます。

## 1. 開発用の隔離と基準の固定（次の作業）

- クラウドでは既存チェックアウトの専用ブランチを使用。勝手にworktreeを増やさない。
- Windows ZIPフォルダーはGitがない可能性がある。Git導入やgit initを無断で行わず、既存フォルダーを保全した別の開発コピーを作る。
- `.venv` はコピー後も絶対パス依存があるため再利用を前提としない。本番の環境や起動バッチを変更しない。
- 開発用DBは明示指定した**コピー**だけを使う。新しいPowerShellの範囲で `MY_AI_ASSET_DB` を設定し、永続的なシステム環境変数を書き換えない。
- 初回起動前にコピー先の解決パスを確認し、元DBへの参照が残っていれば起動しない。外部DB指定や両方のdataフォルダーがあるケースを必ず確認する。
- 一時テスト以外でseed・初期化・DB削除を実行しない。

## 2. NEXTの最初の単位：判断と見送りの記録

追加予定の情報：判断ID、銘柄識別、検討日時、購入検討/見送り/保留、理由、予算・NISAの確認状態、使用した評価ルールと評価履歴ID、根拠の日時。訂正はイベントとして追記し、元の判断は残す。

next_decisions / next_decision_events等の**新規テーブル名は仮案**とし、既存テーブルと衝突しないことを先に確認する。削除可能な候補カタログへの強制依存を避け、コードと名称を当時の値で保存する。保有残高や取引の記録とは別にする。

機能は初期値で無効とし、既存画面での表示・計算・API回数が変わらないことを検証する。売買実行、購入実績の自動生成、未知NISA枠の推測は入れない。

## 3. 判断が変わった理由と予算影響

既存の評価履歴を読み、数値・データ基準日・更新状態・評価ルールの変化を区別する。ルールが違う点数を同じ尺度として差引しない。欠損解消による点数確定と投資魅力の変化を区別する。

実残高を変更しない仮想配分で、既存積立のみと候補追加を比較する。同じ投入額・費用条件・価格基準日で試算し、不明な費用や単元未満株可否は保留する。投信の内部構成がなければ完全な重複率を作らない。

## 4. 精度検証

- 10〜20銘柄を同じ基準日の公式資料と照合。違いを取得失敗/定義差/日付差/丸め/株式分割/資料不足に分け、単純な一致率だけで改善とみなさない。
- 各候補が当時使用できたデータだけを保存し、将来の決算や後日の改訂値を過去判断へ混ぜない。
- 検証可能な履歴が揃ってから、保有・見送りの両方、上場廃止、費用、投入金額を揃えた事後比較を設計する。今回バックテストは実装しない。
- 業種別の財務指標・評価配点の変更は、基準と別期間での検証を先に定義し、旧ルールと新ルールをバージョンで区別する。

## 5. DB移行と復旧

移行は「既存スキーマの読取確認 → バックアップ → バックアップの整合性/コピー復元検証 → コピーDBで追加テーブル/索引だけを試す → 旧データ差分確認 → 回帰テスト」の順序。

既存表のDROP、既存行のDELETE/一括UPDATE、金額型の一斉変換、未知の表の整理はこの計画に含めない。移行の再実行で重複しないこと、失敗時に中途半端な状態が残らないことを試す。移行前後で口座・残高・取得原価・積立・取引・監査・SBI/PayPay区分を照合する。

復旧検証はバックアップを**別の一時パス**へ復元して行い、本番を上書きしない。本番への切替が必要になったときはアプリ停止後、切替前のDBをさらに保管する。旧アプリ・旧DB・WALを混ぜたり、新しいデータが入ったDBを古い版で無条件に開いたりしない。

## 完成条件（将来の実装ごと）

- 基準236件に失敗・無効化・期待失敗の追加がない。追加機能を検証するテストも通る。
- NEXT無効時に既存8画面・予算・損益・取込・APIキー参照が変わらない。
- 本番と開発コピーのパスが異なり、旧データ・未知のテーブルを保全できている。
- 欠損、古いデータ、429、同時更新、二重登録、取引取消、訂正、NISA未確認、単元株/未満株、手数料不明を確認する。
- Windows実機で既存の起動.batとアプリが使え、バックアップからのコピー復元も確認する。
- 機能・変更ファイル・テスト・未対応事項を具体的に報告してから運用切替を行う。
