## Windowsで実施するバックアップの基準（手順準備のみ）

1. 待受ポート・PID・作業フォルダーを照合し、使用しているアプリとDBを確定する。3版が同時に見つかっているため、他のDBを同じものとみなさない。
2. 確認したアプリをCtrl+Cで停止する。他の版が同じDBを使っている場合は、その版も個別に確認してから止める。ブラウザーを閉じるだけでは背景ワーカーは止まらない。
3. 元アプリの外側に新しい日時付きバックアップフォルダーを作る。既存バックアップを上書きしない。コード/設定と、確定したDBを保全する。外部パスのDBを忘れない。
4. DBは標準sqlite3の `mode=ro` URIでソースを開き、SQLite backup APIで新規バックアップを作る。`src.db.session.connect()` を呼ばない。WALのコミット済み情報を含める。
5. 元とバックアップでquick_check、foreign_key_check、テーブル/列の一覧と表ごとの件数を確認する。異常や既存の外部キー問題があれば記録して止まり、勝手に修復しない。未知の旧テーブルも保全する。
6. `.streamlit/config.toml` と使用中の秘密設定をPC内のバックアップへ複製する。秘密設定を複製した場合は、値やハッシュを報告書に出さず、元とのバイト一致の成否だけを記録する。共有フォルダーやGitへ置かない。
7. グローバルStreamlit設定が実参照元なら、プロジェクトのsecretsだけで完了扱いにしない。環境変数由来のキーをTOMLや平文ログへ勝手に書き出さない。
8. バックアップDBを別の一時パスへ復元し、整合性とスキーマ・件数を再確認する。本番DBへ復元しない。
9. バックアップ先・検査の成否・使用したアプリの版だけを記録する。鍵・銘柄明細・口座情報をチャットやGitへ送らない。

既存 `tools/windows_update.py:backup_database()` には読取専用ソース＋SQLite backup API＋quick_checkの実装があります。236件の基準テストには、この機能のWAL保全テストを含みます。ただし、実アプリを更新する `prepare_release()` や自動更新.batを今回のバックアップ目的で実行してはいけません。現在のコードの関数を使う場合も、Windows側の版を先に確認します。

秘密設定のバックアップそのものには元のAPIキーが含まれます。これはPC内での復旧専用コピーであり、画面・ログ・調査報告・Gitへの出力には使いません。実DBと秘密設定のZIPをこのチャットへアップロードする必要はありません。
